# 自我檢討循環（三天一輪）

這個 Skill 會一邊用一邊改。每天記錄，三天整理一次，經使用者同意才改進 GitHub。

## 存放位置

都在使用者資料夾的 `HOME_DIR/紀錄/`（見 SKILL.md 第 0 步）：

| 檔案 | 內容 |
|---|---|
| `評分/YYYY-MM-DD-scorecard.md` | 當天評分紀錄（格式見 `scorecard.md`） |
| `修改案/YYYY-MM-DD-proposal.md` | 當天修改案；開頭寫「第 N 輪第 N 天」，第 3 天那份就是本輪合併修改案 |
| `source-registry.md` | 來源登記表（見 `source-registry.md`） |

已經推到 GitHub 的改動以 Git 的 commit 紀錄為準，不另外存檔。

## 每天（做完當天的簡報之後）

1. 照 `scorecard.md` 打分：主分析者自評＋獨立 agent 評分，寫進當天評分紀錄。
2. 記下使用者今天的更正、追問與偏好（用使用者自己的話）。
3. 寫當天修改案 `修改案/YYYY-MM-DD-proposal.md`（開頭寫第幾輪第幾天），每一條要有：
   - **問題**：哪一份、哪一項分數低，或使用者說了什麼。
   - **原因**：是這次執行草率，還是 Skill 規則本身不清楚／缺漏？只有後者才改 Skill。
   - **修改**：要改哪個檔案、改成什麼（寫出新文字）。
   - **怎麼驗證**：下次哪個分數應該變好。
4. 把當天分數和修改案的重點用一兩句告訴使用者，附上檔案。當天不改 GitHub。

## 第 3 天（循環結束）

1. 讀這輪三天的評分紀錄與修改案，合併成一份**本輪修改案**：
   - 三天平均分數（每份、每項），和上一輪比較。
   - 重複出現的問題優先；只出現一次、而且是執行草率的，不改規則。
   - 同一條規則上輪才改過、這輪分數沒變好的，標出來討論要不要撤回。
   - 來源登記表的狀態變動。
2. 把本輪修改案給使用者看，**等使用者同意**（可以只同意其中幾條）。
3. 使用者同意後：只把同意的那幾條改進 Skill，commit 到 GitHub（commit 訊息寫第幾輪、改了哪幾條）。隔天的修改案從下一輪第 1 天開始。
4. 使用者還沒回覆就不推；下一輪照常開始，未決的修改案帶到下一輪。

## 原則

- 改 Skill 是為了下次做得更好，不是讓分數好看：不要為了加分而放寬評分標準。
- 評分標準（`scorecard.md`）本身也可以改，但要在修改案裡單獨列出，並說明為什麼。
- 雙方評分一致不代表正確；使用者更正永遠優先。
